# TELTEST Stage 08.2 — Multi-provider destinations

در نسخه 0.8.2 هر جاب انتقال می‌تواند بین 1 تا 20 مقصد مستقل داشته باشد. هر مقصد پروایدر، شناسه کانال/گفت‌وگو، روش ارسال و وضعیت اجرای خودش را نگه می‌دارد.

## پروایدرهای اجرایی

| کد | پروایدر | اعتبارنامه | روش ارسال |
|---|---|---|---|
| `telegram_user` | تلگرام با اکانت کاربری | Session متصل TELTEST | کپی یا فوروارد |
| `telegram_bot` | Telegram Bot API | Bot Token | کپی |
| `bale` | Bale Bot API | Bot Token | کپی |
| `eitaa` | EitaaYar API | Token | کپی |
| `rubika` | Rubika Bot API | Bot Token | کپی |

برای ارسال به پروایدرهای Bot/API، اکانت تلگرام انتخاب‌شده در جاب استخراج محتوای مبدا و رسانه را می‌خواند؛ سپس همان محتوا با API پروایدر مقصد ارسال می‌شود.

## رابط کاربری

در فرم «انتقال جدید»، دکمه «اضافه‌کردن پروایدر» یک ردیف مقصد تازه می‌سازد. هر ردیف شامل موارد زیر است:

- انتخاب پروایدر؛
- انتخاب اکانت مقصد برای انتقال کاربری تلگرام؛
- شناسه کانال یا گفت‌وگوی همان پروایدر؛
- روش `copy` یا `forward`، در صورت پشتیبانی؛
- حذف مقصد از جاب.

همین ویرایشگر در صفحه ویرایش جاب هم وجود دارد. صفحه مشاهده جاب، آمار کل و وضعیت هر مقصد و هر پست را نشان می‌دهد.

## مدل اجرا و خطا

- برای هر ترکیب «پست × مقصد» یک رکورد مستقل در `transfer_job_items` ساخته می‌شود.
- مقصدها به‌ترتیب اجرا می‌شوند و خطای یک مقصد مانع تلاش برای مقصد بعدی نمی‌شود.
- وضعیت هر مقصد مستقل است: `pending`، `running`، `completed` یا `failed`.
- رویدادهای `DESTINATION_STARTED`، `DESTINATION_FINISHED` و `DESTINATION_FAILED` در لاگ همان جاب ثبت می‌شوند.
- وضعیت هر پست مستقل است: `listed`، `transferring`، `transferred`، `failed` یا `skipped`.

## سازگاری

کدهای قدیمی `telegram` و `telegram_mtproto` هنگام نصب به `telegram_user` مهاجرت می‌کنند. جاب‌ها، پست‌ها، مقصدها، Sessionها و تنظیمات قبلی حذف یا بازنویسی نمی‌شوند.

## محدودیت این مرحله

اجرای انتقال هنوز هم‌زمان با درخواست وب انجام می‌شود. Worker مستقل، صف پس‌زمینه، Retry زمان‌بندی‌شده و Backoff در مراحل بعدی اضافه خواهند شد.
